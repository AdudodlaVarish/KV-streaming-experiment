# Diagnostic accounting correction, before main evaluation

The frozen design anticipated equality between lost computed positions and scheduled replay, as in the earlier studies. The aggressive guard_fast diagnostic reveals two terminal evictions where already-in-flight final tokens complete the request while its context is evicted. Those contexts never need replay. In that diagnostic, 2,014,015 positions were evicted, 2,010,561 were scheduled again, and 3,454 positions belonged to terminal contexts retired on stale final output (1,791 and 1,663). Client output targets and native success counts still agree exactly.

The policy, parameters, compiled native scheduling port and workload matrix remain frozen and unchanged. The analyzer now independently replays the trace accounting: each preemption records its computed prefix; each native step verifies replay against the pending prefix; terminal stale completion retires remaining replay debt. For each request, **lost positions = scheduled replay + terminal discarded positions**, with no pending debt at completion. Requests/episodes distinguish these cases; no-replay terminal evictions are excluded from eviction-to-replay wait coverage. This corrects the prospective accounting assumption rather than selecting or removing a poor-performing run. All diagnostic data are retained and excluded from main results.

The diagnostics also show that deadline pursuit can create very large replay volumes. That performance behavior is retained for evaluation, not treated as an instrumentation failure or reason to tune parameters.
